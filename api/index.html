    API reference¶

    This document describes the public Python API surface of abstractvision (0.x / Alpha) and points to the implementation.

    See also: - Getting started (end-to-end examples): docs/getting-started.md - Architecture (how the pieces fit): docs/architecture.md - Backends reference (support matrix): docs/reference/backends.md - FAQ (common questions): docs/faq.md

    Public exports¶

    The package exports the following symbols from abstractvision (see ../src/abstractvision/__init__.py):

    • VisionManager
    • ProviderAdapterInfo
    • ProviderModelInfo
    • VisionAdapterCapabilitiesRegistry
    • VisionModelCapabilitiesRegistry
    • LocalAssetStore
    • RuntimeArtifactStoreAdapter
    • LoRAAdapterSpec
    • is_artifact_ref
    • __version__

    Core concepts¶

    Tasks¶

    VisionManager exposes one method per task (implementation: ../src/abstractvision/vision_manager.py):

    • generate_image(...) → text_to_image
    • generate_image_batch(...) → repeated text_to_image orchestration with explicit seed planning
    • edit_image(...) → image_to_image
    • edit_image_batch(...) → repeated image_to_image orchestration with explicit seed planning
    • upscale_image(...) → image_upscale
    • generate_video(...) → text_to_video (backend-dependent)
    • generate_video_batch(...) → repeated text_to_video orchestration with explicit seed planning
    • image_to_video(...) → image_to_video (backend-dependent)
    • image_to_video_batch(...) → repeated image_to_video orchestration with explicit seed planning
    • video_to_video(...) → video_to_video (backend-dependent)
    • upscale_video(...) → video_upscale (backend-dependent)
    • generate_angles(...) → multi_view_image (API exists; no built-in backend implements it yet)

    Task names are also used by the capability registry (../src/abstractvision/assets/vision_model_capabilities.json).

    Backends¶

    Backends are execution engines that implement the VisionBackend interface (../src/abstractvision/backends/base_backend.py).

    Built-in backends live in ../src/abstractvision/backends/: - OpenAICompatibleVisionBackend (HTTP) - HuggingFaceDiffusersVisionBackend (local Diffusers images; local Diffusers text_to_video groundwork is currently quarantined) - StableDiffusionCppVisionBackend (local stable-diffusion.cpp / GGUF) - MLXGenVisionBackend / compatibility alias MFluxVisionBackend (local Apple-first MLX-Gen bridge for curated AbstractFramework q4/q8 MLX presets, official FIBO snapshots, shared LoRA adapters, and Wan video)

    Backend config classes are re-exported from abstractvision.backends via lazy imports (see ../src/abstractvision/backends/__init__.py).

    Provider catalog listing is exposed as a backend contract:

    from abstractvision.backends import OpenAICompatibleBackendConfig, OpenAICompatibleVisionBackend

backend = OpenAICompatibleVisionBackend(
    config=OpenAICompatibleBackendConfig(base_url="http://localhost:1234/v1")
)
for model in backend.list_provider_models(task="text_to_image"):
    print(model.id)

    For official OpenAI, use base_url="https://api.openai.com/v1" and an API key. Catalog listing is explicit and does not change the configured generation model.

    When AbstractVision is loaded as an AbstractCore capability plugin, the plugin shim exposes the same explicit catalog surface as llm.vision.list_provider_models(task="text_to_image"). It returns JSON-safe dictionaries so Core/Gateway route code can avoid private backend reach-throughs.

    Adapter inventory is exposed through the same explicit pattern:

    for adapter in backend.list_provider_adapters(
    model="AbstractFramework/qwen-image-edit-2509-8bit",
    task="image_to_image",
):
    print(adapter.id)

    ProviderAdapterInfo rows are explicit discovery outputs. They do not mutate the configured generation route.

    Outputs: bytes vs artifact refs¶

    VisionManager returns:

    • GeneratedAsset (bytes) when no store is configured (../src/abstractvision/types.py)
    • an artifact ref dict when VisionManager.store is configured (via MediaStore.store_bytes(...))

    Artifact helpers and stores are defined in ../src/abstractvision/artifacts.py.

    Image sizes are backend/model-specific. width and height arguments are optional request overrides; omitting them lets the backend use its default or auto behavior. Passing an unsupported size is expected to fail at the selected provider/backend boundary rather than being silently rewritten by AbstractVision.

    VisionManager (orchestrator)¶

    VisionManager is intentionally thin: it validates/gates best-effort and delegates to the configured backend.

    Signature (see ../src/abstractvision/vision_manager.py): - backend: a VisionBackend implementation (required to run anything) - store: optional MediaStore to enable artifact-ref outputs - model_id: optional capability-gating model id (must exist in the registry) - registry: optional VisionModelCapabilitiesRegistry instance (reused when gating is enabled)

    Minimal example (OpenAI-compatible backend + artifact refs)¶

    from abstractvision import LocalAssetStore, VisionManager, is_artifact_ref
from abstractvision.backends import OpenAICompatibleBackendConfig, OpenAICompatibleVisionBackend

backend = OpenAICompatibleVisionBackend(
    config=OpenAICompatibleBackendConfig(base_url="http://localhost:1234/v1")
)
store = LocalAssetStore()
vm = VisionManager(backend=backend, store=store)

ref = vm.generate_image("a studio photo of an espresso machine", width=768, height=768, steps=20)
assert is_artifact_ref(ref)
png_bytes = store.load_bytes(ref["$artifact"])

    Local example (Diffusers backend)¶

    Install abstractvision[diffusers] before using this backend.

    from abstractvision import LoRAAdapterSpec, VisionManager
from abstractvision.backends import HuggingFaceDiffusersBackendConfig, HuggingFaceDiffusersVisionBackend

backend = HuggingFaceDiffusersVisionBackend(
    config=HuggingFaceDiffusersBackendConfig(
        model_id="runwayml/stable-diffusion-v1-5",
        device="auto",
        allow_download=False,
    )
)
vm = VisionManager(backend=backend)
asset = vm.generate_image("a watercolor painting of a lighthouse", width=512, height=512, steps=10)

    Note: allow_download=False is the default. Pre-download model weights separately, or set allow_download=True only when you want runtime downloads.

    upscale_image(...), generate_video(...), and image_to_video(...) are part of the public API. MLX-Gen 0.40.3+ supports SeedVR2 image_upscale, Wan text_to_video, and first-frame image_to_video, including A14B task-specific checkpoints. Local Diffusers video remains experimental and disabled from the normal local surfaces. Generated MP4 outputs still require an ffmpeg executable on PATH whenever a backend returns frame sequences for local packaging.

    ImageGenerationRequest includes typed control_image and control_strength fields: a structure guide such as edges, sketch, or pose, not a source-image edit input. MLX-Gen applies them on AbstractFramework/qwen-image-8bit (see Control image) and refuses a control_image on any other model (field="control_image") and a control_strength given alone (field="control_strength"); the other built-in backends refuse a control_image and do not use control_strength.

    Local example (MLX-Gen backend)¶

    Install abstractvision[mlx-gen] and pre-download the exact model repo first, for example abstractvision download AbstractFramework/wan2.2-t2v-a14b-diffusers-8bit --provider mlx-gen.

from abstractvision.backends import MLXGenBackendConfig, MLXGenVisionBackend

def on_progress(event):
    if event.total_frames:
        print(f"{event.phase}: frame {event.frame}/{event.total_frames}")
    else:
        print(f"{event.phase}: step {event.step}/{event.total_steps}")

image_backend = MLXGenVisionBackend(
    config=MLXGenBackendConfig(model="AbstractFramework/flux.2-klein-9b-8bit")
)
image_vm = VisionManager(backend=image_backend)

image_asset = image_vm.generate_image(
    "a studio product photo of a red toy race car",
    width=768,
    height=512,
    steps=12,
    guidance_scale=1.0,
    on_progress=on_progress,
)

# A plain edit runs FLUX.2's edit route, on which MLX-Gen validated this LoRA on the 8-bit package.

    "Turn this cat into a dog.",
    image=Path("./cat.png").read_bytes(),
    lora_adapters=[
        LoRAAdapterSpec(source="dx8152/Flux2-Klein-9B-Consistency:Flux2-Klein-9B-consistency-V2.safetensors")

    on_progress=on_progress,
)

reference_asset = image_vm.edit_image(
    "compose the subject using the second image as a style and layout reference",
    image=Path("./subject.png").read_bytes(),

    guidance_scale=1.0,
    on_progress=on_progress,

upscale_backend = MLXGenVisionBackend(config=MLXGenBackendConfig(model="AbstractFramework/seedvr2-3b-8bit"))

    Control image (control_image)¶

    On AbstractFramework/qwen-image-8bit, the only model whose MLX-Gen rows have a control route (qwen.control), generate_image(..., control_image=...) runs QwenImageControlNet with the row's ControlNet (InstantX/Qwen-Image-ControlNet-Union:diffusion_pytorch_model.safetensors); control_strength is a finite number (unset: the engine CLI's 0.4). The ControlNet's side weights are looked up in the Hugging Face cache before any weights load and never downloaded during a generation: when they are missing the request is refused (field="control_image") with the command that fetches them, abstractvision download InstantX/Qwen-Image-ControlNet-Union. get_capabilities().supports_control_image is true on that model only. i2i refuses control_image and control_strength (field=).

    Video-to-video (video_to_video)¶

    VisionManager.video_to_video(prompt, video, **kwargs) (VideoToVideoRequest; the plugin's v2v(prompt, video, ...)) edits a source clip. video is its bytes, written once to the run's directory, or a local file Path the engine reads in place (the plugin takes a file path, bytes or an artifact ref). On MLX-Gen it runs Wan 2.2 T2V-A14B's video-to-video route (Wan2_2_TI2V) with the A14B defaults and memory plan of text-to-video:

    • Guidance as the engine CLI sets it on this route: unset, 4.0 and guidance_2 3.0; a guidance_scale set alone leaves guidance_2 to the engine, which then uses the same value (text-to-video and image-to-video keep guidance_2 at the model's default).
    • video_strength in (0, 1] (unset: the engine's 0.8) and an optional mask (one image, white is the region to change; one with no white pixel raises ValueError). A negative prompt is passed only when set, so the model's own default applies.
    • Before any weights load, the clip is probed by the engine's rule: one too short for num_frames at fps is refused (field="num_frames"); extra takes the progress callbacks, max_sequence_length and vae_tiling (as on the other Wan routes), and any other key is refused naming it.
    • The result is the engine's MP4 (the source's audio is not carried; the engine records whether there was one) and num_frames is the engine's count, snapped down to 4n+1.

    Wan 2.1 VACE 1.3B (Wan-AI/Wan2.1-VACE-1.3B-diffusers, WanVace; defaults 832x480, 81 frames at 16 fps, 30 steps, guidance 5.0) runs the same task with other controls: reference_images (images in order, no published maximum), masked_region_mode ("generate" or "repaint" the region the mask marks; it needs a mask) and conditioning_scale (a finite number, default 1.0). It takes no video_strength and no guidance_2 (one transformer), and refuses them by name; T2V-A14B refuses the three VACE fields the same way. A VACE preload loads WanVace and runs no warm-up generation; in "default" it reads the transformer and the VAE ahead, as the other Wan preloads do.

    TI2V-5B and I2V-A14B have no video-to-video route and refuse the task, as do the other backends.

    Video restoration (video_upscale)¶

    VisionManager.upscale_video(video, **kwargs) (VideoUpscaleRequest; the plugin's upscale_video(video, ...)) restores a clip on SeedVR2 3B or 7B (MLX-Gen 0.40.2 and later). video is handled as for video-to-video. The options are resolution (unset: 1x), softness ([0, 1], unset: 0.0), start_seconds (unset: the clip's start), max_frames (unset: to its end), seed, quantize (as for upscale_image) and drop_audio (True: the result is always silent, MLX-Gen does not copy the source's soundtrack; unset or False: MLX-Gen copies it, and fails the run after the restoration when it cannot). Before any weights load, MLX-Gen's own plan (SeedVR2VideoRestorePlan.for_video, the one mlxgen upscale --video-path uses) probes the clip and decides the chunking and the memory profile, counting the model's weights as loaded when this backend already holds the instance the run reuses:

    • a scale above 1x is refused (CapabilityNotSupportedError, field="resolution", supported=None), and a clip beyond the safe memory profile or below its temporal quality floor is refused (field=None), each with MLX-Gen's message (on the safe profile's 48 GB budget a frame of up to about 1.4 megapixels fits, 1280x720 included; a larger one is refused with the largest size that fits); MLX-Gen's argument errors (start_seconds below 0, max_frames below 1) stay ValueError, as does a clip it cannot decode ("video is not a readable clip"); an extra key other than the progress callbacks is refused naming it (vae_tiling included).
    • The run applies the plan as the CLI does: MLX-Gen's low-RAM saver keeping the transformer, in memory_mode="default" and "low" alike ("lowest" is refused); metadata reports the mode asked and low_ram: true. The MLX cache limit is one value from before the model loads to the end of the run: the plan's (8 GB, what MLX-Gen's CLI runs with on any Mac, above its default cap where that is lower), except that a limit the host set (by MLX-Gen's own rule: one at or below half of physical memory found before its default applied) is never raised, so the smaller of the two applies; the limit in force before the run is restored after it. The run drops the model at its end, so a later image upscale loads a fresh one.
    • The result is an MP4 whatever the source's container (as MLX-Gen writes it: H.264, and AAC for the source's audio, which MLX-Gen copies); metadata["mlx_gen"] is its sidecar. Progress is per chunk; a cancel removes the partial output.

    Wan 2.2 A14B has two guidance controls. Use guidance_scale for the primary/high-noise stage and guidance_2 for the second/low-noise stage. The registry default is guidance_2=3.0 for text-to-video A14B and 3.5 for image-to-video A14B. Other video models should omit guidance_2 unless their registry task declares it.

    For TI2V-5B, use flow_shift directly when you need to override the route default. The bundled visual proof uses 832x480 with flow_shift=3.0.

    Wan video defaults come from one per-model table, WAN_VIDEO_DEFAULT_CANVASES in ../src/abstractvision/backends/mflux.py: 832x480 for every Wan model, 121 frames at 24 fps and 50 steps for TI2V-5B, 81 frames at 16 fps and 40 steps for the A14B models. Any field you pass (width, height, num_frames, fps, steps) overrides the default; backend.list_provider_models(task="text_to_video") reports the same values in each model's raw["parameter_defaults"]. The Wan VAE decode runs in overlapping spatial tiles by default, which bounds its memory; pass extra={"vae_tiling": False} to decode whole frames at once. Generated asset metadata records vae_tiling. Measured memory per size: docs/faq.md. MLX-Gen encodes the prompt with its UMT5 text encoder in float32 on the GPU: with mlx-gen 0.40.2 and later a new prompt is encoded in seconds, a prompt already used is served from MLX-Gen's on-disk cache, and results for a given prompt and seed differ slightly from those made with mlx-gen 0.40.1; see MLX-Gen's Wan prompt encoding.

    For MLX-Gen, on_progress receives an abstractvision.VideoProgressEvent. Image generation/editing/upscaling events carry phase, step, total_steps, and denoise-step progress. Wan video events add frame, total_frames, and frame_progress. The lower-level backend.generate_image_with_progress(...), backend.edit_image_with_progress(...), backend.upscale_image_with_progress(...), backend.generate_video_with_progress(...), and backend.image_to_video_with_progress(...) methods keep the existing two-argument (current, total) callback for backend-agnostic progress bars. For MLX-Gen, that callback reports denoise step counts; use on_progress(event) when a UI also needs video frame context.

    MLX-Gen image routes¶

    MLX-Gen publishes, per model, the routes it can run (its capability rows, backend.describe_routes()), and mlxgen generate picks one with its planner. The MLX-Gen backend asks the same planner for every image_to_image request on FLUX.2, Z-Image and base Qwen-Image, and for a request on any model that sets an option only a route applies (image_strength below). The route it selects decides the MLX-Gen class and call; other requests run as in 0.3.37. On a model the engine publishes no rows for (a local folder whose own name it cannot place), the model has its 0.3.37 tasks, and an option runs its 0.3.37 branch on the families 0.3.37 applied it on (image_strength on ERNIE-Image-Turbo, reference images on FLUX.2 and Qwen-Image-Edit, a mask on Qwen-Image-Edit and FIBO-Edit) and is refused on any other with field=<option>, supported=(). On every MLX-Gen image route, text-to-image included, a negative prompt is passed where the row of the route the request runs takes one (supports_negative_prompt) and dropped silently where it takes none; a model without rows keeps 0.3.37's answer. parameter_constraints["negative_prompt"] in list_provider_models() says the same. A request is refused before any weights load, in normalize_image_edit_request as in edit_image:

    • with ValueError when two of its options contradict each other (mask with image_strength), or a value is not of its type (a picture that fails to decode, checked once the route takes it);
    • with CapabilityNotSupportedError(field=<option>, supported=()) when no row of the model applies an option it sets, and field="lora_adapters" when the selected row takes no adapters;
    • with CapabilityNotSupportedError(field=None, supported=None) and the planner's message when no row serves that combination of options.

    Those are check point 1, from the request's values and the engine's rows. An outpaint or a reframe adds check point 2 at the start of edit_image, still before any weights load: the source is written to the run's directory and MLX-Gen's canvas session is built from it, which refuses a box it cannot apply and a two-pass outpaint in low-RAM mode. A caller who only calls normalize_image_edit_request sees check point 1 only.

    Latent image-to-image (image_strength)¶

    ImageEditRequest.image_strength (edit_image(..., image_strength=0.6), the plugin's i2i(image_strength=...)) noises the source before denoising, in (0, 1]; a value outside is refused with field="image_strength". On MLX-Gen, extra["image_strength"] is the same option (both set and different: ValueError); the other backends refuse the typed field and pass extra on unchanged.

    • FLUX.2 klein: setting it selects the latent route (Flux2Klein); without it an edit stays the reference edit (Flux2KleinEdit).
    • Base Qwen-Image (AbstractFramework/qwen-image-8bit, the Qwen-Image-2512 packages): image_to_image runs latent (QwenImage), at image_strength=0.4 when the request names none; so do Z-Image and Z-Image-Turbo (ZImage). ERNIE-Image-Turbo runs latent as before.
    • Qwen-Image-Edit, FIBO, Fibo-lite and FIBO-Edit have no latent route and refuse it (field="image_strength", supported=()).

    list_provider_models() publishes parameter_defaults["image_strength"] = 0.4 and parameter_constraints["image_strength"] = {"min": 0.0, "min_exclusive": true, "max": 1.0} for every model with a latent route.

    FLUX.2 masked edits (mask)¶

    On FLUX.2 klein, an edit with a mask runs Flux2KleinInpaint (route flux2.inpaint): white in the mask is the region to change (MLX-Gen reads its luminance, resizes it to the canvas and ignores an alpha channel; the bytes are passed unchanged). The mask is decoded first, and one that is not a picture raises ValueError naming mask. An unset guidance_scale stays unset, so the class applies its default (4.0 on the base models, 1.0 on the distilled ones); the base models take a negative prompt. get_capabilities().supports_mask is true on FLUX.2 klein. A masked edit and a plain edit run on different classes, so alternating them reloads the model each time (never two instances at once).

    On Z-Image-Turbo a mask runs its masked edit (route z-image.inpaint, the mask instead of a strength); base Z-Image has no masked route and refuses it.

    Multi-reference edits (reference_images)¶

    ImageEditRequest.reference_images lists the images after image, in order: bytes, or local file paths the engine reads in place (the plugin's i2i(reference_images=...) and i2i_batch take bytes-like values, file paths (any path-like) and artifact refs, and pass bytes). On MLX-Gen, extra["reference_images"] is the same option, and the 0.3.37 keys extra["images"], ["additional_images"] and ["image_paths"] keep working but raise ValueError with the typed list. The request runs MLX-Gen's multi-reference route: FLUX.2 klein (Flux2KleinEdit) and Qwen-Image-Edit 2509 and 2511 (QwenImageEdit); the first image decides the canvas, and no maximum count is published or enforced. A model without that route (plain Qwen-Image-Edit, ERNIE, base Qwen-Image) refuses it (field="reference_images", supported=()), as does a combination with a mask or a strength (field=None); every picture counts there, those of the 0.3.37 extra keys included, so none is dropped. An empty list is no reference. extra["reference_images"] is read as 0.3.37 read it (any iterable; None and blank items skipped), and only what that reading keeps counts; the typed field takes a list of image bytes or paths.

    Outpaint and reframe¶

    outpaint_padding grows the canvas by a box in MLX-Gen's syntax ("top,right,bottom,left", each in pixels or "N%"; one to four values) and fills the new area, keeping the source; reframe_padding grows it the same way and lets the model recompose the whole picture. They run MLX-Gen's own canvas session (mflux.outpaint), which builds the conditioning canvas, plans the passes and owns the canvas size, so extra["width"] / ["height"] are refused with them (field="width"). FLUX.2 klein runs outpaint with Flux2KleinOutpaint and reframe (distilled weights only) with Flux2KleinEdit; Qwen-Image-Edit runs both with QwenImageEdit.

    • outpaint_fill is one of the route's fill modes (FLUX.2: auto, edge, neutral, solid, blur; unset: auto), outpaint_fill_color ("R,G,B" or "#rrggbb") the color of outpaint_fill="solid". Qwen-Image-Edit's fill is fixed (edge) and refuses both, and either one without an outpaint is refused.
    • A box that pads both axes deeply runs as two passes (MLX-Gen's auto plan); progress counts the steps across both, and memory_mode="low" refuses it (field="memory_mode", supported=("default",): low-RAM mode frees the transformer the second pass needs). An unset guidance_scale stays unset, so the class applies its default.
    • A box outside MLX-Gen's validated envelope runs, as on the engine's CLI; metadata["outpaint_warnings"] says so, and metadata["outpaint_notice"] gives the resolved canvas and passes. The engine's geometry fields are under metadata["mlx_gen"].

    extra["strength"] (the CLI's --strength, the plugin's strength=) is the 0.3.37 cross-backend keyword, not a second spelling of the typed field: on every route 0.3.37 had it keeps exactly its 0.3.37 meaning (clamped to [0, 1], dropped when not a number, ignored by the FLUX.2 and Qwen-Image-Edit reference edits), and on the latent routes new in 0.3.38 it is read as the run's strength with the same clamp. It never selects a route and is not read on a masked route. Combined with image_strength it raises ValueError.

    Memory modes (memory_mode)¶

    Every generation request (generate_image, edit_image, upscale_image, generate_video, image_to_video and their _batch variants) takes memory_mode: "default", "low" or "lowest" (MEMORY_MODES in ../src/abstractvision/types.py). The lower modes trade speed for a lower memory peak. A request that names no mode uses $ABSTRACTVISION_MEMORY_MODE, else "default"; a request value always wins. The environment value is one setting for every backend in the process: a backend that cannot honour it runs the lowest-memory mode it lists that is not below it ("lowest" becomes "low" where "low" is listed, else "default") and logs that once per process, while a mode passed on the request is refused. On MLX-Gen, every mode starts with the engine's default MLX cache cap, as its CLI applies it (total RAM / 8, between 1 and 8 GiB, once per process; a limit the host set at or below half of physical memory is left alone, a higher one is replaced by the default cap). "low" then lowers it to 1 GB for the run. backend.preload(memory_mode=None, quantize=None) loads the model as a request carrying those values would, so the first such request reuses it: the values are checked by the same function as a request's, before anything loads, with the same refusals; memory_mode=None is the process default under the same rule. A backend that takes no load-time quantize refuses quantize there. On MLX-Gen, preload() loads the model as the first request with those values starts it (under the same 1 GB cache hold in "low" and "lowest") into the instance that request reuses, so in a mode whose runs drop the model ("low", "lowest", and every mode on Wan TI2V-5B, which releases its denoiser before the decode) the preloaded instance serves one request. In "default" an MLX-Gen preload warms exactly what a run of its task reads, so the first request reads no weights (MLX-Gen binds them lazily at load): an image task (text-to-image, image-to-image, upscale) runs one warm-up of that task on its plain route, its output discarded, with a small ordinary request: a neutral 256x256 picture or canvas (352 on base Qwen-Image, FIBO and Fibo-lite, 384 on FIBO-Edit, 512 on ERNIE-Image-Turbo and Bonsai, the smallest side MLX-Gen runs those families at) at 2 steps, or for SeedVR2 a 64x64 picture at 1x; a backend whose default_width / default_height are set warms at that canvas instead. A video task, whose warm-up run would take minutes, reads the first denoiser and, where the run encodes an input (image-to-video, video-to-video), the VAE (the Wan A14B second expert is read at the switch, as in a run; MiniMax-H3 reads its transformer at load). "low" and "lowest" read nothing ahead. preload(..., warm_up=False) skips all of it: the model is still resolved (its files found), checked (MLX-Gen version, the task, the memory mode and quantize) and built, so a bad model fails at the preload and not at the first request, but nothing is run or read ahead, and the first request reads the weights as a request without a preload does, minus the construction; backend.preload_warmed() says which the held model got. When anything in a preload fails, the model it loaded is dropped before the error is raised. A preload refused for its values, or one that fails after reusing the model already held, leaves that model held. The MLX-Gen backend's preload also takes task, the task the host is about to run, as a hint: when the model has that task, the model is loaded as a request of that task loads it (on FLUX.2 klein, task="image_to_image" loads Flux2KleinEdit, the class of a plain or multi-reference edit; a latent, masked or outpaint request then rebuilds its own class), and when it does not, or task is None, the preload chooses as before. task is never a reason to refuse; the other backends' preload takes no task.

    asset_or_ref = vm.generate_video(
    "a red fox trots through fresh snow",
    memory_mode="low",
)
    Backend low lowest
    MLX-Gen, image and edit routes MLX-Gen low-RAM mode, as mlxgen generate --low-ram: a 1 GB MLX cache from before the model loads to the end of the run, and mlx-gen's MemorySaver, which tiles the VAE decode, frees the text encoders before the denoising loop and the transformer after it. low plus transformer block streaming (--stream-blocks), on a model whose MLX-Gen routes stream transformer blocks: accepted for MiniMax-H3, refused on every other current catalog model.
    MLX-Gen, Wan video As mlxgen generate --low-ram on one seed: the 1 GB cache, the MLX cache cleared after every step and transformer block, the denoisers released before the decode and, on the A14B models, the inactive expert released. Refused on every current Wan route.
    MLX-Gen, MiniMax-H3 The 1 GB cache and the transformer freed before the decode (release_transformer=True); the next request loads the model again. low plus block streaming (stream_blocks=True). Refused with load-time quantize, and with an adapter that trains the AdaLN projections.
    MLX-Gen, SeedVR2 upscale As mlxgen upscale --low-ram on images: the 1 GB cache only. SeedVR2 keeps its own tiling and the loaded model. Refused (SeedVR2 has no block streaming).
    Diffusers on CUDA Model CPU offload. Sequential CPU offload.
    Diffusers on CPU or MPS Refused. Refused.
    stable-diffusion.cpp CPU offload of the model parameters: --offload-to-cpu for sd-cli, offload_params_to_cpu for the Python binding. Refused.
    OpenAI-compatible Sent to a remote that lists the mode for the model in GET /vision/models (AbstractCore's server); refused otherwise. As low.

    A mode named on the request that the backend cannot honour for its configured model and device raises CapabilityNotSupportedError before any model loads or any request is sent, whether the call comes through VisionManager, the AbstractCore plugin or a direct backend call. extra={"memory_mode": ...} is read the same way as the keyword (on a backend that applies quantize or the soundtrack fields, so are those keys of extra; elsewhere they pass through extra unchanged); a keyword and an extra value that disagree raise ValueError.

    Placement is fixed when a model loads, so a request may only raise it. On Diffusers, the CPU offload that runs is the higher of the configured cpu_offload (or what "auto" picks) and the one the request needs; a loaded pipeline with less offload than a request needs is loaded again, and one with more offload keeps serving later requests until it is unloaded. stable-diffusion.cpp keeps an operator's --offload-to-cpu and loads the Python binding again with offload_params_to_cpu when a low request needs it.

    On MLX-Gen, low trades residency for memory: image, edit, Wan and MiniMax-H3 runs free parts of the model, so the instance is dropped when the run ends, whatever its outcome, and the next request loads it again, a preloaded resident model included; MiniMax-H3 runs in lowest are dropped the same way. A batch (generate_image_batch, generate_video_batch, ...) is a series of such requests: each item loads the model, frees it and drops it, so every item peaks as one low run, at the cost of one load per item (building the instance took 1.3 to 3.1 s for MiniMax-H3 8-bit, 0.5 to 2.5 s for FLUX.2 [klein] 9B 8-bit and 1.4 to 2.7 s for Wan 2.2 T2V-A14B 8-bit; the weights are then read during the run). SeedVR2's low is the cache limit alone, and it keeps its instance. low and lowest hold a 1 GB MLX cache limit for the run, never above a limit already in force; default runs leave the limit to MLX-Gen. MLX-Gen holds one instance at a time: a request whose model, adapters, quantize or block streaming differ from the loaded instance's releases it, and clears the MLX cache, before the new one loads.

    Discovery: backend.get_capabilities().memory_modes lists the modes a backend can honour for its configured model and device; Diffusers with device="auto" lists "default" on macOS (no CUDA) without importing torch, and elsewhere asks torch, importing it once. Each MLX-Gen provider catalog entry carries raw["parameter_constraints"]["memory_mode"] = {"enum": [...]}, where enum holds the modes that model can honour. The result metadata records the mode a run used as memory_mode, "default" included: Diffusers, stable-diffusion.cpp and MLX-Gen on every run (MLX-Gen also records low_ram and stream_blocks; stable-diffusion.cpp records offload_to_cpu; Diffusers records cpu_offload), and the OpenAI-compatible backend when the remote reports it.

    Video with sound (MiniMax-H3)¶

    The MLX-Gen backend serves MiniMax-H3, which generates a video with a synchronized stereo soundtrack: text_to_video, and image_to_video from a first frame. The catalog entry is MiniMaxAI/MiniMax-H3; the published packages are AbstractFramework/minimax-h3-8bit (64.3 GiB, recommended), AbstractFramework/minimax-h3-bf16 (115.1 GiB) and the mixed AbstractFramework/minimax-h3-4bit (44.9 GiB). The packages hold the base weights; base_model picks the schedule: minimax-h3-turbo-544p (8 steps, 960x544), minimax-h3-turbo (8 steps, 1344x768) or minimax-h3 (50 steps).

    from abstractvision import VisionManager
from abstractvision.backends.mflux import MLXGenBackendConfig, MLXGenVisionBackend

backend = MLXGenVisionBackend(config=MLXGenBackendConfig(
    model="AbstractFramework/minimax-h3-8bit", base_model="minimax-h3-turbo-544p"))
clip = VisionManager(backend=backend).generate_video(
    "A red fox trots through fresh snow at dawn.",
    soundscape="Soft crunch of paws in dry snow, faint wind.", music="Sparse piano.",
    width=640, height=352, num_frames=124, seed=42, memory_mode="low")

    Request fields (on VideoGenerationRequest and ImageToVideoRequest):

    Field Meaning
    prompt The visual description, or a complete structured prompt with its section labels. Passed to MLX-Gen unchanged; MLX-Gen composes the structured prompt (and, for a first frame, its picture reference).
    soundscape, music The overall_soundscape and non_diegetic_music sections.
    generate_audio False writes a silent clip. Default: the soundtrack is generated. A boolean: any other type, the string "false" included, is refused.
    flow_shift, audio_shift The video and audio schedule shifts (MLX-Gen video_shift / audio_shift), positive numbers.
    width, height Given together; positive multiples of the route's dimension_multiple (32), with an aspect ratio inside MLX-Gen's window (1:4 to 4:1). Unset: the schedule's canvas, or for a first frame MiniMax-H3's own mapping of the keyframe's aspect ratio, which must then lie in the same window.
    num_frames Rounded up by MLX-Gen to the next count of its grid (17n+5 at 24 fps, 124 to 345): 125 runs as 141. A count that rounds outside that range (below 108, or above 345) is refused before any weights load.
    steps, seed, quantize, memory_mode, cancel_event As for other routes; steps is at least 1 and seed lies in [0, 2**64 - 1] (MLX's random key). quantize applies to the source snapshot only (8 or 4, the row's validated_quantization_bits).
    lora_adapters Adapters on the transformer role (the row's lora_target_roles). As in MLX-Gen, the list replaces the Turbo adapter a Turbo schedule attaches: include the Turbo file to keep the 8-step schedule.

    Values left unset stay unset, so MLX-Gen applies the schedule's own defaults. Everything is checked before any weights load, against MLX-Gen's capability row and its own MiniMax-H3 planning code, and a refusal about one field names it (a refusal about two fields together, such as lowest with quantize, leaves field None):

    • What the route cannot apply, or a value outside what it accepts, raises CapabilityNotSupportedError: negative_prompt, guidance_scale, guidance_2, an fps other than 24, an extra key other than the progress callbacks and memory_mode, a canvas off the multiple or outside the aspect window, a frame count that rounds outside 124 to 345 (a count inside is rounded up to the grid, not refused), steps below 1, a shift that is not positive.
    • A value of the wrong type, or two fields that contradict each other, raises ValueError: a width that is not an integer, soundscape or music that is not a string, a non-boolean generate_audio, a prompt that already carries an overall_soundscape: (or non_diegetic_music:) section together with soundscape= (or music=), which MLX-Gen's own prompt composition refuses.
    • A first frame is opened and decoded first: empty or undecodable bytes raise ValueError naming image. Wan routes check their values and keyframes the same way, with the same error types.
    • memory_mode="lowest" with an adapter that trains the transformer's AdaLN projections (checked with MLX-Gen's own adapter test) is refused, naming the adapter: MLX-Gen must then hold the whole transformer in memory.

    Every number the backend checks comes from MLX-Gen (the capability row, its aspect window); describe_routes() returns the row. Wan and the other local backends refuse soundscape, music, generate_audio and audio_shift; the OpenAI-compatible backend sends them to a remote that advertises them for its model and refuses them otherwise (backends).

    The result is the MP4 with its AAC soundtrack. GeneratedAsset.audio is a GeneratedAudioTrack (sample_rate, channels, duration_seconds, muxed, codec); when MLX-Gen could not mux the track, muxed is false and data holds it as WAV bytes. GeneratedAsset.audio_summary() reports the soundtrack in the one shape every layer uses (None without one):

    {"present": True, "sample_rate": 32000, "channels": 2, "codec": "aac",
 "muxed": True, "duration_seconds": 5.1667}

    codec is the WAV's ("pcm_s16le") when the track is not muxed, and the summary then adds "wav": the WAV bytes on the asset, the stored WAV's artifact ref once stored. With a store, VisionManager stores such a WAV as an artifact of its own (tags modality: audio) and records the summary as audio in the video's stored metadata and in the returned ref. metadata carries prompt (the composed prompt), seed, steps, width, height, num_frames, requested_frames, duration_seconds, the two shifts, and mlx_gen: MLX-Gen's own metadata sidecar (<clip>.metadata.json), including its audio mux facts and runtime_memory (the process's memory at the end of the save, peaks included).

    Memory modes: low sets the 1 GB MLX cache and release_transformer=True: the transformer is freed before the decode, the model is dropped when the run ends, and the next request, a batch item included, loads it again. Every low clip then peaks the same: 24.7 GiB for a 640x352, 124-frame clip with the 8-bit package, alone, in sequence or in a batch. lowest adds block streaming (stream_blocks=True): each transformer block is read from disk for the length of its call (10.6 GiB on the same clip), and the next request also loads the model again. It works from a prepared package or from the 16-bit source, and is refused with quantize. MLX-Gen's measured peaks for each package and mode are in the route row's measured_runs; abstractvision show-model MiniMaxAI/MiniMax-H3 prints them per package, with the smallest memory each mode was tested on. When MLX-Gen's preflight finds that a run cannot fit, the backend raises GpuOutOfMemoryError naming the memory_mode the run used and the lower modes to try.

    The weights are never downloaded during generation, even with allow_download=True: the catalog marks the downloads that only an explicit download fetches (explicit_download: true), today the three AbstractFramework packages and the source repository MiniMaxAI/MiniMax-H3. The packages are gated, and the MiniMax H3 Community License's grant excludes the European Union, the United Kingdom, the Republic of Korea and the United States of America (the source repository is not gated; the same licence applies). Accept the licence on the package page while logged in to Hugging Face and download explicitly: abstractvision download MiniMaxAI/MiniMax-H3 fetches the recommended 8-bit package (--bits 4 or --bits 16 the others), and --base-model minimax-h3-turbo-544p (or minimax-h3-turbo) also caches the Turbo adapter that schedule loads. minimax-h3 loads no adapter. See Downloads.

    Host integration¶

    What an application embedding VisionManager can rely on:

    • Engine metadata. MLX-Gen results carry the engine's metadata under metadata["mlx_gen"] (image, edit, upscale and video routes).
    • Cancellation. Every request takes cancel_event (anything with is_set(), such as threading.Event). A set event stops an MLX-Gen run at its next progress event, between denoising steps, and raises GenerationCancelledError. What stays loaded after a cancelled run depends on the family:
    • image, edit, Wan A14B and MiniMax-H3 keep the model in "default", and SeedVR2 in every mode;
    • Wan TI2V-5B always drops it (it releases its denoiser before the decode);
    • image, edit, Wan A14B and MiniMax-H3 runs in "low" (MiniMax-H3 in "lowest" too) drop it, a batch item included.

    The GenerationCancelledError an MLX-Gen run raises carries no traceback of the run, so a caller that keeps it holds none of the run's memory.

    Diffusers and stable-diffusion.cpp check the event before a run starts; the OpenAI-compatible backend cancels its remote job on a remote that advertises the vision routes for the model, and elsewhere (the OpenAI API, a remote without those routes, a model the remote does not list) checks the event only before sending. Such a request runs there as a job, which AbstractCore's server refuses while another generation runs (a request without cancel_event waits instead); the backend raises that as a RuntimeError saying so. get_capabilities().cancellation is "step" or "start". - Load-time quantize. quantize (bits) on generation requests. get_capabilities().quantize_bits lists the widths the configured model accepts: the route's validated_quantization_bits, else MLX-Gen's --quantize choices (for MiniMax-H3, its own 8 and 4). A prepared package (its shards carry MLX-Gen's metadata, or the catalog lists it as a prepared or sub-16-bit package) lists none and refuses it, as do the other local backends; the OpenAI-compatible backend sends it to a remote that advertises it. - Metadata without local paths. MLX-Gen results report the model as its repo id (a Hugging Face cache snapshot) or its directory name (another local path), and adapters the same way (org/name:file.safetensors, or the file name): every field of the engine's metadata that holds a path (model, lora_paths, lora_application_reports, the file video_health checked, the original_* fields an upscale copies from its input), in metadata["mlx_gen"] and its top-level copies, and requested_lora_adapters; the fields naming the files AbstractVision wrote for a run (image_path, image_paths, masked_image_path, video_path, audio_sidecar_path) are left out. - Route rows. vm.describe_routes(model=None, task=None) returns MLX-Gen's capability rows (schema 17) as JSON: canvas and frame rules, defaults, LoRA, audio, memory (measured_runs, peaks), quantization. Other backends return []. - Progress. on_progress(event) receives VideoProgressEvent with phase, step, total_steps (and frame, total_frames on video) as MLX-Gen emits them. An exception raised in a progress callback is logged once per run and does not stop the run; use cancel_event to stop one. - Embedding. import abstractvision and constructing a VisionManager write no files, set no environment variables, configure no loggers and import neither AbstractCore nor an engine. MLX-Gen is imported at the first capability lookup or model load; its own import sets TOKENIZERS_PARALLELISM=false when unset.

    Shared LoRA adapters¶

    AbstractVision exposes a typed LoRA contract across Python, CLI, and the AbstractCore plugin through LoRAAdapterSpec plus the request field lora_adapters=[...].

    Each adapter can carry:

    • source
    • scale
    • weight_name
    • subfolder
    • adapter_name
    • target_role

    Wan TI2V-5B uses one role, transformer. Wan A14B routes require explicit high_noise_transformer / low_noise_transformer assignment. Provider catalogs surface exact-route LoRA truth through supports_lora, lora_status, lora_target_roles, and lora_validation_profile.

    Passing advanced backend parameters (extra)¶

    Request dataclasses include an extra: dict field (../src/abstractvision/types.py). Use it to pass backend-specific parameters in a controlled way:

    asset_or_ref = vm.generate_image(
    "a product photo of a matte black espresso machine",
    steps=8,
    guidance_scale=1.0,
    extra={
        # Compatibility-only keys used by older Diffusers flows:
        "rapid_aio_repo": "linoyts/Qwen-Image-Edit-Rapid-AIO",
    },
)

    Backends may ignore unknown keys; consult the backend implementation and docs/reference/backends.md. New callers should prefer the typed shared lora_adapters field instead of extra["loras*"]. Legacy Diffusers compatibility payloads such as loras_json still work, but they are no longer the preferred public contract.

    Capability registry (what models can do)¶

    The packaged registry is loaded by VisionModelCapabilitiesRegistry (../src/abstractvision/model_capabilities.py).

    from abstractvision import VisionModelCapabilitiesRegistry

reg = VisionModelCapabilitiesRegistry()
print(reg.list_tasks())
print(reg.models_for_task("text_to_image"))

reg.require_support("runwayml/stable-diffusion-v1-5", "text_to_image")

    Optional gating: - If you construct VisionManager(model_id=..., registry=...), the manager will fail fast on unsupported tasks before calling a backend (../src/abstractvision/vision_manager.py).

    Important: the registry is not a guarantee that your configured backend can execute a task at runtime. Use docs/reference/backends.md for backend support.

    Downloads and what is cached¶

    The download presets live in ../src/abstractvision/model_downloads.py; the state of a preset on this host in ../src/abstractvision/model_inventory.py. The CLI's download, catalog, show-model and models --json are built on them.

    from abstractvision.model_downloads import download_model_preset, plan_model_preset_download, select_download_preset
from abstractvision.model_inventory import preset_status

preset = select_download_preset("MiniMaxAI/MiniMax-H3")          # the recommended package: AbstractFramework/minimax-h3-8bit
preset = select_download_preset("MiniMaxAI/MiniMax-H3", bits=4)  # AbstractFramework/minimax-h3-4bit
print(preset.gated, preset.license_name, preset.recommended)  # from the catalog
plan = plan_model_preset_download(preset, base_model="minimax-h3-turbo-544p")  # reads the Hub listings; downloads nothing
print(plan.summary_lines(), plan.disk_space_error())  # access, sizes, files complete / to fetch, free disk space
print(preset_status(preset))  # cache / cache_bytes / cache_gaps / snapshot_dir / memory_modes / memory_peaks
snapshot_dir = download_model_preset(preset, base_model="minimax-h3-turbo-544p", report=print)
    • select_download_preset(name, *, target, engine, bits, allow_non_8bit): the preset abstractvision download fetches, with its flags. The host's order picks the target, preferring an 8-bit package unless allow_non_8bit or an MLX-Gen engine or target is named (target or engine restricts it; bits keeps one width). Within that target a single package is selected, and several select the one the catalog marks recommended; with none recommended, ValueError lists them, whatever the flags narrowed them to. Without the 8-bit preference a repository named exactly selects that repository instead of a package made from it, on every host. A Hugging Face owner/name the catalog does not name is the whole repository (repository_preset). find_model_preset(name, *, target, engine, require_8bit, bits, download_rule=False) is the catalog lookup it is built on; without download_rule (as the backends resolve a configured model), several packages with none recommended resolve by the catalog's own order (qwen-image to Qwen-Image-2512).
    • download_command(repo_id, *, engine=None, base_model=None): the abstractvision download command that selects exactly repo_id on this host, checked with select_download_preset: abstractvision download MiniMaxAI/MiniMax-H3 --allow-non-8bit for the MiniMax-H3 source repository, abstractvision download AbstractFramework/minimax-h3-8bit for a package; ValueError when no form of the command selects it, or when the catalog lists the repository but not for engine (a repository outside the catalog is fetched whole, whatever the engine).
    • plan_model_preset_download(preset, *, base_model, model_dir, token, all_files): a DownloadPlan, read from the Hub listings without writing anything. parts are the repositories the download fetches from (DownloadPart: role, plan): the package, a stable-diffusion.cpp bundle's companions (vae, llm), and the adapter of the MLX-Gen schedule base_model unless mlx-gen finds it cached (adapter, adapter_path). Each part's plan is a HubDownloadPlan: files (each a HubFile with name, size, complete (its snapshot link or blob is in the cache, huggingface_hub's own test) and partial (the bytes its .incomplete file holds)), complete_files, fetch_files, total_bytes, complete_bytes, fetch_bytes, partial_bytes, required_bytes, free_bytes, commit (the commit the listing named, which the fetch takes), gated, listing_error (why there is no listing; the byte counts are then None). The DownloadPlan adds the totals, legacy_import / legacy_remove (a legacy tree), summary_lines(), disk_space_error() (the message when the files to fetch do not fit under DISK_RULE, else None) and to_dict(). download --dry-run prints it. Raises HuggingFaceAccessError when the Hub refuses a repository, ValueError when base_model is not a schedule of the package, and OptionalDependencyMissingError when the adapter can only be named by mlx-gen and mlx-gen cannot be imported.
    • DISK_RULE: the files to fetch count at their full size, less what their partial .incomplete files already hold, because huggingface_hub writes each file into that same file (continuing it over plain HTTP, rewriting it from the start over Xet).
    • download_model_preset(preset, *, base_model, model_dir, token, max_workers, all_files, report): plans first and passes the summary to report. A legacy <model_dir>/<preset.local_dir_name> tree (legacy_model_tree) is moved into the cache and used as the package as it is (report says it was not compared with the Hub). Raises InsufficientDiskSpaceError (a RuntimeError) before anything is written when the files to fetch do not fit; fetches exactly the files to fetch of every part (none when every file is complete), from the commit each listing named, and records that commit as the repository's main; raises HuggingFaceAccessError when the Hub refuses a repository (naming the licence when the catalog marks it gated) and RuntimeError when files are missing after the download. Without a listing it uses what a local look finds in the cache as it is when it finds every part, else raises RuntimeError saying why there is no listing and what to do. Returns the package snapshot.
    • repository_preset(repo_id): a repository the catalog does not list, downloaded whole through the same plan.
    • local_cache_state(preset): the local look the listings use, offline: snapshot_dir, files, bytes, gaps (what it can see is missing: partial files, links without content, weight files an index names, components model_index.json names whose folder the preset's patterns name, no weight file) and state (cached, incomplete or absent). No gap does not prove the snapshot holds every file the package selects; only the plan can tell.
    • preset_status(preset): cache, cache_bytes, cache_gaps and snapshot_dir (from local_cache_state), memory_modes (what the backend serving the preset honours on this host; None when that backend cannot run here) and, for MLX-Gen prepared packages whose capability rows publish measured runs, memory_peaks (below) and smallest_tested_memory_gb (per mode, the smallest unified memory mlx-gen completed a run of that width on, where it publishes it). The figures are read from the installed mlx-gen at run time.
    • memory_peaks(repo_id): MLX-Gen's measured runs for one catalog package, as JSON rows {task, memory_mode, width, height, frames, steps, peak_bytes, machine_total_ram_bytes} (peak_bytes is the whole-process footprint, machine_total_ram_bytes the memory of the Mac it ran on), kept to the package's stored width. A run names its canvas, frames and steps but not the schedule it ran with, and mlx-gen publishes the same runs on every MiniMax-H3 schedule (all at 8 steps), so the rows are per package, not per schedule. Empty for a repository that is not a prepared MLX-Gen package of the catalog, or when mlx-gen is not installed or publishes nothing; no model is built.
    • abstractvision.backends.mflux.resolve_mlx_gen_schedule_adapter(base_model, download=False): the adapter an MLX-Gen schedule loads (the MiniMax-H3 Turbo LoRA) and where mlx-gen finds it, or None when the schedule loads none. abstractvision download --base-model fetches the adapter through its plan (into huggingface_hub's cache, where mlx-gen looks), not with download=True.

    Errors you may want to handle¶

    Common exceptions (defined in ../src/abstractvision/errors.py):

    • BackendNotConfiguredError (calling VisionManager without a backend)
    • CapabilityNotSupportedError (task isn’t supported by the model registry or backend, or the backend does not accept the requested memory_mode or another typed option)
    • GenerationCancelledError (the request's cancel_event was set)
    • UnknownModelError (model id isn’t present in the registry)
    • OptionalDependencyMissingError (backend dependency is missing, e.g. Diffusers/Torch)
    • GpuOutOfMemoryError (a CUDA out-of-memory during a Diffusers generation: the message names the model's size, its placement, what was free and what to change: a smaller canvas or fewer steps, sequential CPU offload, or the GGUF path; raised instead of torch's traceback. On MLX-Gen MiniMax-H3 routes, raised when MLX-Gen's preflight reports that the weights or a run cannot fit, naming the memory_mode it used and the lower ones; MLX-Gen reports this for MiniMax-H3 only)
